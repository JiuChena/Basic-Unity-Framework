# 运行流程

## 1. 项目启动

构建入口目前是 `Assets/Scenes/Preload.unity`。场景中的 `Preloader` 会在 `Start` 阶段读取 Inspector 中配置的 Addressable key，并并行预加载对应资源。

```text
Preload.unity
    -> Preloader.Start
        -> AddressableManager.AcquirePersistentAssetAsync<T>(key)
        -> 将 Lease 保存在 Preloader
    -> Preloader.OnDestroy
        -> 逐个 Dispose Lease
```

`AcquirePersistentAssetAsync` 将 Lease 归入 `ResourceScope.Persistent`，因此只应使用于确实需要常驻的启动资源。普通界面、临时特效和玩法资源应使用普通 `ResourceScope`，在所属对象结束时 Dispose。

## 2. GAS 生命周期

`GameplayAbilitySystem` 的生命周期与它 Inspector 中的能力配置列表顺序严格一致。

```text
Awake
    创建 AbilityOwnerContext(gameObject)
    遍历 AbilityDefinitionSO
        CreateRuntime()
        AbilityInit(ownerContext)

OnEnable
    AbilityOnEnable()

Start
    AbilityStart()

Update
    AbilityUpdate(Time.deltaTime)

FixedUpdate
    AbilityFixedUpdate(Time.fixedDeltaTime)

LateUpdate
    AbilityLateUpdate(Time.deltaTime)

OnDisable（反序）
    AbilityOnDisable()

OnDestroy（反序）
    AbilityDispose()
```

### 顺序为什么重要

例如输入能力先写、BHSM 后读：

```text
InputListenerAbilityRuntime.AbilityUpdate
    -> InputRuntimeData.WriteMove / WriteButtonState

BetterHSMAbilityRuntime.AbilityUpdate
    -> BetterHSM.Update
    -> 状态中断方法读取 InputRuntimeData
```

若将 BHSM 放在输入能力前，状态机读取的是上一帧输入，通常会表现为一帧延迟。框架不会替开发者排序；配置列表就是明确依赖声明。

### Gizmo 流程

`GameplayAbilitySystem.OnDrawGizmos` 只遍历配置 SO 并调用：

```csharp
definition.GizmoDraw(gameObject);
```

这条流程在编辑模式可运行，但不会创建 `AbilityOwnerContext`、Ability Runtime、PlayerInput 或任何附加组件。需要 Scene 绘制的 Ability 应将纯配置保存在 SO 中，重写 `GizmoDraw`；不要在 Gizmo 内初始化运行时逻辑。

## 3. 输入到状态决策

```text
PlayerInput / InputActionAsset
    -> InputListenerAbilityRuntime
        -> InputRuntimeData
            -> AbilityOwnerContext[Input]
                -> 业务 Ability 或状态上下文
                    -> StateBase.Interrupt()
                        -> BetterHSM 仲裁
```

### 持续输入

移动是持续值。输入能力每帧将 `Vector2` 标准化后写入 `InputRuntimeData.Move`。状态上下文通过阈值判断是否存在移动输入：

```csharp
return inputRuntimeData.Move.sqrMagnitude > 0.0001f;
```

### 按钮边沿

按钮通过 `InputButton` 枚举和位掩码记录 Held、Pressed、Released 与已消费状态。典型规则：

```text
Interrupt() 中：WasPressed(Jump) 只判断
OnEnter() 或跳跃 Ability 中：ConsumePressed(Jump) 真正消费
```

不要在 `Interrupt()` 里消费输入。因为同一帧一个来源状态会评估所有边，提前消费会使转换结果依赖边的注册顺序。

## 4. BetterHSM 帧循环

```text
BetterHSMAbilityRuntime.AbilityUpdate
    -> BetterHSMAbilityContext.Update（仅 Runtime 内部可调用）
        -> BetterHSM.Update
            -> 当前状态的 StateInterruptContainer.TryEvaluate
                -> 扫描全部转换边
                -> 选择 priority 最大的命中边
                -> 同优先级保留先注册的边
            -> 没有切换：CurrentState.OnUpdate()
            -> 有切换：旧状态 OnExit()，目标状态 OnEnter()
```

每帧最多切换一次，并且发生切换的帧不执行目标状态的 `OnUpdate()`。这避免一个帧内多次跳转和状态重入的不确定性。

状态图在 `Build(initialState)` 后封口；运行期不允许动态添加状态或转换边。若角色有特殊规则，应该在初始化注册方案中注入额外 `Func<bool>` 边，而不是在 Update 中改图。

## 5. BehaviorEditor 运行流程

```text
业务宿主创建 BehaviorExecutor(ownerGameObject)
    -> Play(BehaviorClip)
        -> 读取 BehaviorPlaybackSettings
        -> BehaviorTrackData.CreateExecutor(context)
        -> 按 ExecutionOrder 排序
        -> 每条轨道 Begin()

业务宿主每帧调用 Tick(deltaTime)
    -> 推进行为播放头
    -> 每条轨道 Tick(elapsedTime)
    -> 根据 WrapMode 处理 Once / Loop / ClampForever

停止或替换行为
    -> 每条轨道 Stop()
    -> 清理执行器列表
```

`BehaviorExecutor` 不继承 MonoBehaviour，因此业务宿主决定在哪个生命周期推进它。通常在宿主的 `Update` 中 `Tick(Time.deltaTime)`；若业务需要固定物理时钟，可明确在固定帧推进，但同一个执行器只能由一个时钟驱动。

## 6. 资源与对象池流程

```text
AcquireAssetAsync<T>(key, scope)
    -> 得到 ResourceLease<T>
    -> 使用 lease.Asset
    -> 用完 Dispose lease 或 Dispose scope
        -> 引用计数归零
        -> Addressables.Release(handle)
        -> 广播 OnResourceReleased
        -> 依赖该资源的对象池自动清理
```

对象池中的对象并不代替资源 Lease。池自行使用 Addressable 预制体时，持有对应 Lease；池依赖的资源释放时会清空池，避免保留指向已释放资源的实例。

## 7. 交互流程

```text
InteractSearcher.Update
    -> 按间隔 Physics.OverlapSphere
    -> 获取 Interactable 并调用 CanInteract
    -> 生成 / 回收 InteractOption
    -> 玩家选择选项
    -> 按 F
    -> InteractOption.ExecuteInteract
    -> Interactable 的 UnityEvent
```

`Interactable.Interact(GameObject)` 同时调用 UnityEvent 和可重写的 `OnInteracted`。当前 `InteractOption.ExecuteInteract()` 调用的是注入的 UnityEvent，因此如需让交互选项自动执行子类的 `OnInteracted` 逻辑，需要在业务层明确让事件调用 `Interactable.Interact(interactor)`，或扩展该链路；不要假定选项会自动传入交互者。
