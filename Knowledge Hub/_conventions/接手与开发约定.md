# 接手与开发约定

## 给新 Agent 的起步顺序

1. 读 `HOME.md`，确认当前模块边界和已删除的旧体系。
2. 读与任务直接相关的 `modules/` 和 `templates/` 笔记。
3. 用 `rg` 搜索现有相似实现、调用点与资源引用，不凭印象造新抽象。
4. 先报告发现、依赖和最小实施方案；框架级变更必须先获得用户确认。
5. 修改后运行针对性的编译或验证，检查 Console；更新知识库。

## 当前明确的架构决策

- GAS 的 `GameplayAbilitySystem` 是实体 Ability 的唯一 MonoBehaviour 入口。
- Ability Runtime 与 BHSM 状态都为纯 C#；不要给每种 Ability/状态再加挂载组件。
- 组件依赖由实际使用它的 Ability Runtime 获取和缓存，不由 GAS 公摊。
- Ability SO 保存静态配置；Runtime 保存逻辑与实体引用；RuntimeData 保存可共享的实体动态数据。
- Input Ability 只读取输入并写 `InputRuntimeData`；不驱动移动或状态机。
- BetterHSM 只做状态仲裁与生命周期；不直连 PlayerInput、CharacterController、Animator 或玩法业务。
- BetterHSM 状态图在初始化注册阶段一次性 Build，运行期封口。
- BehaviorEditor 核心不认识任何具体轨道；轨道通过 Compiler Attribute 自动发现。
- 资源加载使用 Addressable Lease/Scope；对象池不替代资源生命周期。
- `DataProvider`、`UnitMover` 和其旧兼容链路已删除，不得因新功能需要而重新引入。

## 代码风格关键点

- 优先 ASCII，现有中文注释与 Tooltip 遵循项目文件编码。
- 类级 summary 保持一句话。
- 类字段都写用途注释；复杂方法按逻辑段落写简短注释。
- 私有方法若只有一两行、只有一处调用且没有稳定语义，应内联，不为了整齐而包装。
- Update/FixedUpdate/LateUpdate 不做分配、资源加载、反复 Find/GetComponent、Instantiate/Destroy。
- 短单行 `if` 不展开花括号；多行逻辑展开。
- Unity Inspector 字段使用 `SerializeField`、`Tooltip`、`Header`，不要把运行时缓存暴露成配置。

## 删除与重构规则

删除旧代码前：

1. `rg` 搜索类名、方法名、枚举值与资源 GUID；
2. 列出全部引用；
3. 区分当前工作区用户已删除文件与本轮要删除文件；
4. 有资源/场景/Prefab 引用时先让用户确认迁移或删除；
5. 不使用 `git reset --hard`、`git checkout --` 或恢复用户已有改动。

当前工作区可能处于未提交的破坏式重构过程。看到删除状态不要自动恢复；除非用户明确要求，否则只在自己的任务范围内修改。

## 文档规则

- 修改公共 API、运行流程或模块边界后，更新对应 `modules/` 笔记。
- 新增 Ability、BHSM 方案或 Behavior 轨道后，增加模板引用或使用说明。
- `journal/` 记录当天的长期决策和验证结论，不粘贴大段源码。
- `HOME.md` 只保持导航、关键边界与当前高价值状态。

## 提交前自检

```text
[ ] Unity Console 无编译错误。
[ ] 新旧类型、命名空间、资源 GUID 的引用均已搜索。
[ ] 热路径没有新分配、重复查组件或同步资源加载。
[ ] 生命周期中的事件/Timer/Lease/Scope 都能释放。
[ ] Inspector 只暴露需要配置的数据。
[ ] 没有为单一调用点增加无意义包装。
[ ] 文档与实际代码一致。
[ ] 没有重新引入已废弃的 DataProvider 或 UnitMover 链路。
```
