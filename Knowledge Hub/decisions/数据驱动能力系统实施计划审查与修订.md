# 数据驱动能力系统实施计划审查与修订

## 一、审查范围

本文审查《数据驱动能力系统实施计划》的设计可行性，并将其整理为后续实施依据。

本次只修改知识库文档，不修改代码、不创建场景、不替换现有模块。

审查时重点对照以下现有能力：

- `DataProvider/Blackboard`：提供单位运行时数据，不承担能力调度。
- `BehaviorCore`：提供行为时间线、动画片段、Hitbox 和表现事件解释。
- `Gameplay Effects`：提供效果定义、运行时效果实例、Tick 和单位效果容器。
- `ObjectsPool`、`VFXPool`、`AudioManager`：提供通用表现和对象生命周期能力。
- `UnitDriverBase`、`StatusData`、Targeting：当前 Gameplay 层单位运行时能力。

## 二、总体结论

原计划的目标是可行的，但不能按“一个 `AbilitySO` 同时保存配置、运行时状态和执行逻辑”的方式直接落地。

需要保留的核心方向：

1. 单位通过一个能力调度入口管理能力，而不是为每个能力增加新的 `MonoBehaviour`。
2. 能力的配置使用 `ScriptableObject` 资产表达，Inspector 通过资产列表完成组合。
3. 能力执行依赖运行时上下文，不直接依赖具体单位脚本。
4. 一次性能力和持续能力使用不同的调度语义。
5. 输入由 `DataProvider/Blackboard` 提供，能力系统只消费能力触发契约。
6. 视觉、音频、动画、命中和数值效果复用现有模块，不在能力系统中重新实现。

必须修正的核心问题：

1. `ScriptableObject` 资产不能保存每个单位独有的冷却、计时、目标、完成状态或事件句柄。
2. `AbilityContext` 不能演变成持有所有系统的万能上下文。
3. `AbilityComponent` 不能同时承担输入采集、目标搜索、动画播放、伤害结算和效果 Tick。
4. 能力系统不能复制 `BehaviorCore` 的行为时间线，也不能复制 `Gameplay Effects` 的效果运行时。
5. “单位只挂一个能力组件”应作为目标形态，而不是第一阶段强制替换现有全部组件。
6. 能力系统必须明确一次能力触发只允许一个调度入口，避免 `Update`、`FixedUpdate` 和外部调用重复执行。

因此，推荐将方案定义为：

```text
AbilityDefinitionSO：只读配置和能力组成定义
AbilityRuntime：每个单位、每次激活独立的运行时状态
AbilityComponent：Unity 外壳、资产索引和调度器
AbilityContext：按能力执行阶段提供的最小依赖视图
现有模块：负责动画、表现、目标、效果、移动和数据
```

## 三、现有系统边界

### 3.1 DataProvider / Blackboard

`DataProvider` 的职责是将输入设备、AI 或其他数据源转换为单位运行时可消费的数据。

它不应负责：

- 判断能力是否可以释放；
- 管理能力冷却；
- 保存能力执行状态；
- 创建能力实例；
- 驱动能力动画或效果。

能力系统可以从 Provider 的 Blackboard 读取通用能力触发数据，例如：

```text
AbilityCommand
AbilitySlot / AbilityKey
TriggerVersion
TargetRequest
```

但这些数据是否存在、具体属性名称和业务能力映射，不应塞入基础 `Blackboard`。建议由业务黑板声明能力触发属性，能力组件通过应用层接口读取。

### 3.2 BehaviorCore

`BehaviorCore` 已经负责：

- 播放 `BehaviorClip`；
- 推进动画段时间线；
- 触发 VFX、音频、投射物和 Gameplay Effect 事件；
- 执行 Hitbox 检测；
- 处理行为停止、循环和完成。

能力系统不应再次实现：

- 动画时间线；
- Hitbox 逐帧扫描；
- VFX/Audio 事件解释；
- 投射物发射细节。

推荐关系：

```text
AbilityRuntime
    -> 请求 BehaviorCore 播放一个 BehaviorClip
BehaviorCore
    -> 按时间线驱动动画、Hitbox 和表现事件
```

能力是“为什么执行”和“执行哪一个行为”的编排者，`BehaviorCore` 是“行为如何按时间线执行”的运行时。

### 3.3 Gameplay Effects

现有 `EffectDefinitionSO`、`GameplayEffectSO`、`RuntimeEffectInstance` 和 `UnitEffectController` 已经承担效果定义与效果实例运行时。

能力系统不应新增另一套：

- Buff 计时器；
- 持续伤害 Tick；
- 治疗和回能逻辑；
- 效果实例列表；
- 效果停止与清理。

能力只应引用或请求现有 Effect 定义：

```text
AbilityDefinitionSO
    -> 引用 BehaviorClip 或 EffectDefinitionSO
AbilityRuntime
    -> 在合适时机发起执行
UnitEffectController / GlobalEffectSystem
    -> 创建并推进 RuntimeEffectInstance
```

原计划中“持续伤害能力”可以作为示例，但它应展示能力如何触发现有效果，而不是重新实现一套 DoT 系统。

## 四、推荐架构

### 4.1 AbilityDefinitionSO：只保存资产配置

原计划中的 `AbilitySO` 建议更名为 `AbilityDefinitionSO`，直接表达它是“能力定义资产”。

它可以保存：

- 能力唯一键；
- 显示名称和图标；
- 触发类型；
- 冷却配置；
- 资源消耗配置；
- 行为或效果引用；
- 目标规则引用；
- 通用执行参数；
- 子类专有的静态配置。

它不能保存：

- 当前冷却剩余时间；
- 当前目标；
- 当前单位引用；
- 当前执行进度；
- `IsFinished`；
- 当前生成的 VFX、Audio 或 Projectile 句柄；
- 任何会因单位或一次释放而变化的字段。

原因是同一个 `ScriptableObject` 资产可以被多个单位共享。如果把运行时状态写进资产，会产生跨单位串状态：

```text
单位 A 释放火球
    -> FireBallSO.cooldownTimer 被修改
单位 B 使用同一个 FireBallSO
    -> B 错误继承 A 的冷却状态
```

这不是实现细节问题，而是 `ScriptableObject` 共享语义下的架构不变量。

### 4.2 AbilityRuntime：每个单位独立的运行时实例

每个 `AbilityComponent` 应为其资产创建独立的运行时实例，或在首次使用时创建并缓存实例。

运行时实例负责保存：

- 所属单位引用；
- 当前能力状态；
- 冷却剩余时间；
- 当前执行时间；
- 当前目标快照或目标句柄；
- 本次能力生成的可停止句柄；
- 是否完成、取消或失败；
- 本次执行需要清理的临时状态。

建议生命周期：

```text
Create / Bind
    -> Initialize
    -> TryActivate
    -> OnActivated
    -> Tick 或 FixedTick
    -> Complete / Cancel
    -> OnDeactivated
    -> Reset 或 Dispose
```

这里的 `AbilityRuntime` 是纯 C# 运行时对象，不承担 Unity 挂载职责。

### 4.3 AbilityComponent：Unity 外壳和调度器

`AbilityComponent` 可以作为单位的能力入口，但职责必须收敛为：

- 持有 Inspector 中配置的 `AbilityDefinitionSO` 列表；
- 创建和缓存当前单位的 `AbilityRuntime`；
- 解析必要的 Unity 组件和项目接口；
- 接收外部能力命令；
- 按固定顺序驱动能力生命周期；
- 管理能力实例集合；
- 在单位销毁或禁用时清理运行时实例。

它不负责：

- 直接读取键盘；
- 直接查找目标；
- 直接执行伤害和 Buff；
- 直接操作 VFX、Audio、Projectile 的内部实现；
- 直接推进 `RuntimeEffectInstance`；
- 解释具体能力的专有字段。

“唯一 `MonoBehaviour`”应理解为能力系统新增的唯一统一入口，不应理解为单位从此只能保留一个 `MonoBehaviour`。现有 `DataProvider`、`BehaviorInterpreter`、`UnitEffectController` 等组件不能在没有迁移验证的情况下强行删除。

### 4.4 AbilityContext：最小化依赖视图

原计划中的 `AbilityContext` 方向正确，但字段设计过于宽泛。不能长期维护一个不断增加字段的万能上下文。

建议按执行职责拆成窄接口或窄视图：

```text
IAbilityOwnerContext      -> 单位身份、状态、Transform
IAbilityInputContext      -> 当前能力命令和触发来源
IAbilityTargetContext     -> 当前目标查询结果或目标请求
IAbilityExecutionContext  -> 时间、取消、完成和句柄清理
IAbilityMovementContext   -> 需要移动时提供移动策略入口
IAbilityPresentationPort  -> 行为、音频、VFX 等外部请求
```

能力基类只拿到它需要的接口，不把 `UnitDriverBase`、根 `GameObject`、所有组件和所有系统直接塞进去。

`FixedDeltaTime` 可以属于执行上下文；“当前位置/速度”不应默认塞入所有能力上下文，应由需要移动的能力通过 `IAbilityMovementContext` 获取。

## 五、调度模型修订

### 5.1 触发入口

能力系统不直接写死：

```csharp
Input.GetKeyDown(KeyCode.Q)
```

输入应通过 `DataProvider/Blackboard` 或外部命令接口进入能力系统。建议保留两种入口，但统一落到同一个激活方法：

```text
DataProvider/Blackboard
    -> AbilityCommand
    -> AbilityComponent.SubmitCommand

业务代码 / AI
    -> AbilityComponent.TryActivate
```

两条入口不能各自执行能力逻辑，必须汇合到同一套校验和激活流程。

### 5.2 一次性能力

一次性能力不是“完全没有运行时状态”。它仍然可能需要：

- 资源或目标校验；
- 行为播放完成等待；
- 生成投射物后的句柄管理；
- 失败回滚；
- 冷却开始时机。

因此建议语义为：

```text
TryActivate
    -> 校验
    -> 创建本次 AbilityRuntime 或执行实例
    -> OnActivated
    -> 如果立即完成则 Complete
    -> 否则进入运行时集合等待完成
```

不要用 `isContinuous == false` 直接决定“绝不进入集合”。是否进入集合应该由能力运行时状态决定。

### 5.3 持续能力

持续能力进入激活集合后，由统一调度器驱动。建议明确两个阶段：

```text
Update：命令采集、非物理时间推进、目标和输入快照更新
FixedUpdate：涉及 Rigidbody、CharacterController 或物理效果的执行
```

不是所有能力都必须实现两个阶段。能力应通过接口声明自己需要的阶段，组件只调用已声明的阶段，避免所有能力每个物理步都被无条件遍历。

### 5.4 结束和取消

能力结束不应只依赖公开的 `IsFinished` 字段。建议统一定义结果：

```text
Running
Completed
Cancelled
Rejected
Failed
```

结束时必须保证：

- 只执行一次 `OnDeactivated`；
- 释放本次能力创建的句柄；
- 清理能力临时状态；
- 从激活集合移除；
- 冷却按明确规则开始；
- 不影响同一资产的其他单位实例。

## 六、能力、行为和效果的分工

推荐使用以下分工：

| 功能 | 所属模块 | 能力系统的角色 |
|---|---|---|
| 按键、AI、网络命令采集 | DataProvider / 业务输入 | 提供能力触发数据 |
| 能力冷却、消耗、激活条件 | Ability | 负责校验和调度 |
| 动画时间线 | BehaviorCore | 能力请求播放行为 |
| Hitbox 检测 | BehaviorCore | 能力引用或触发行为 |
| VFX、Audio、Projectile 事件 | BehaviorCore / Gear / Gameplay | 能力通过端口或行为事件请求 |
| 伤害、治疗、Buff、回能 | Gameplay Effects | 能力触发现有效果 |
| 移动、冲刺、跳跃 | UnitMover 或独立移动模块 | 能力请求移动策略，不重复实现移动物理 |
| 目标搜索 | Targeting | 能力请求目标结果，不重复查找 |
| 单位生命、能量、死亡状态 | StatusData | 能力读取或通过接口修改 |

特别注意：

- `FireBallAbility` 不应自己实现投射物池化和飞行逻辑，应调用现有 Projectile 接口。
- `DamageOverTimeAbility` 不应自己维护每帧伤害，应创建现有 `RuntimeEffectInstance`。
- `DashAbility` 不应复制 UnitMover 的 Rigidbody 速度和碰撞处理，应使用移动模块提供的能力入口。

## 七、对原实施步骤的修订

原计划中的步骤需要调整为以下顺序：

### 阶段 0：冻结边界和验收场景

先写清楚以下场景，作为实施验收标准：

1. 同一个能力资产被两个单位同时使用，冷却和目标状态互不影响。
2. 玩家通过 DataProvider 触发能力，AI 通过代码命令触发同一能力，最终走同一条激活链路。
3. 能力触发 BehaviorCore 行为，行为完成后能力正确结束。
4. 能力触发 Gameplay Effect，效果由现有效果系统 Tick 和清理。
5. 能力被打断、单位死亡或组件禁用时，动画、音频、VFX 和效果句柄正确清理。
6. 单位销毁后，AbilityRuntime 不再持有 Unity 对象和静态事件引用。

### 阶段 1：只建立运行时契约

先创建最小的纯 C# 契约，不接 Inspector，不接具体技能：

- 能力运行状态和结果；
- 能力命令；
- 激活结果；
- 最小执行上下文；
- 能力运行时生命周期接口；
- 能力输出端口接口。

本阶段的验收重点是状态迁移和清理闭环，不是做出火球效果。

### 阶段 2：创建定义资产和实例化机制

实现 `AbilityDefinitionSO` 与 `AbilityRuntime` 的一对多关系：

```text
一个 AbilityDefinitionSO
    -> 多个 AbilityComponent 引用
    -> 每个 AbilityComponent 创建自己的 AbilityRuntime
```

禁止将运行时状态字段放入 `AbilityDefinitionSO`。

### 阶段 3：实现 AbilityComponent 调度器

只实现：

- 资产列表校验；
- 运行时实例创建和缓存；
- `SubmitCommand`；
- `TryActivate`；
- Update / FixedUpdate 阶段调用；
- 完成、取消和销毁清理。

本阶段不接具体 DataProvider、BehaviorCore 和 Gameplay Effects。

### 阶段 4：接入 DataProvider

定义能力层需要的最小触发契约，再由业务黑板提供对应数据。

不把所有能力字段都加入基础 `CharacterBlackboard`。建议：

- 基础黑板只提供通用输入和通用命令；
- 角色或业务黑板声明能力槽位、目标请求等业务属性；
- AbilityComponent 通过接口读取，不依赖具体 `PlayerBlackboard`。

### 阶段 5：接入 BehaviorCore 和 Gameplay Effects

先做适配器或端口，不让 Ability 直接引用解释器内部状态。

验收：

- 能力触发一个已有 `BehaviorClip`；
- 行为事件能触发已有 VFX/Audio/Projectile；
- 能力触发现有 Gameplay Effect；
- 停止能力时只清理本次实例产生的资源。

### 阶段 6：迁移一个真实能力

只选择一个真实、边界清楚的能力进行迁移。建议优先选择：

- 不涉及复杂目标切换；
- 不涉及移动物理；
- 可以直接复用现有 BehaviorCore 和 Gameplay Effect；
- 有明确开始、完成和取消条件。

不建议第一例选择冲刺，因为它会同时碰到移动、碰撞、动画、输入和打断。

### 阶段 7：逐模块迁移和删除旧组件

只有在新能力系统完成真实场景验证后，才逐步迁移：

- 能力相关的旧挂载脚本；
- 重复的输入入口；
- 重复的效果驱动；
- 重复的表现触发。

删除旧组件前必须搜索全部引用并确认没有其他系统依赖，不允许为了达到“单位只挂一个组件”而提前删除现有能力。

## 八、原计划中需要删除或改写的表述

### 8.1 “AbilitySO 是数据 + 执行逻辑”

改为：

```text
AbilityDefinitionSO 保存能力定义和静态配置；
AbilityRuntime 保存每个单位、每次激活的运行时状态并执行能力逻辑。
```

如果确实需要多态执行逻辑，可以让定义资产创建运行时实例，但逻辑执行时使用实例字段，不把状态写回资产。

### 8.2 “isContinuous 决定是否进入激活集合”

改为：

```text
能力定义可以声明建议的调度阶段；
最终是否进入运行时集合由激活结果和运行时状态决定。
```

### 8.3 “AbilityContext 持有位置、速度、目标等全部数据”

改为按能力需求提供窄上下文或端口，禁止持续向一个 Context 添加字段。

### 8.4 “AbilityComponent 负责输入调度”

改为：

```text
AbilityComponent 接收能力命令并调度；
DataProvider 或业务层负责生成能力命令。
```

### 8.5 “加能力 = 加资产，不改代码”

这句话只能作为配置型能力的目标，不能作为所有能力的绝对承诺。

准确表述应为：

```text
对于已有通用执行能力和端口覆盖的能力，新增实例主要通过资产组合完成；
当出现新的执行范式或新的系统依赖时，仍需要增加框架扩展代码。
```

否则会诱导开发者把越来越多业务分支塞入一个万能基类，最终形成臃肿系统。

## 九、性能和生命周期要求

### 性能

- 不在 `Update` / `FixedUpdate` 中通过名称查找能力、目标或组件。
- 运行时实例、能力索引和激活列表在初始化阶段创建或缓存。
- 激活列表使用可复用集合，避免每帧分配。
- 不在能力 Tick 中使用 LINQ、反射或频繁闭包。
- `AbilityComponent` 只驱动有对应阶段能力，不无条件执行所有资产。
- 目标、动画、效果和表现的高频查询复用现有模块缓存。

### 生命周期

必须覆盖以下退出路径：

```text
正常完成
主动取消
被新能力打断
单位死亡
组件禁用
场景卸载
单位销毁
```

每条路径都要保证：

- 不重复结束；
- 不残留循环音频；
- 不残留 VFX 或投射物句柄；
- 不遗留效果实例；
- 不让运行时实例持有已销毁 Unity 对象；
- 不把状态写入共享 `ScriptableObject`。

## 十、待确认决策

在阶段 1 开始前需要确认：

1. `AbilityDefinitionSO` 是否采用纯定义资产命名，运行时类型固定为 `AbilityRuntime`。
2. 能力冷却由 `AbilityRuntime` 保存，还是由统一的能力冷却服务保存。当前推荐前者，减少全局状态。
3. 能力命令是作为业务黑板属性提供，还是由独立 `IAbilityCommandSource` 提供。当前推荐两者都可适配，但最终只进入一个 `SubmitCommand` 入口。
4. 能力触发 `BehaviorCore` 时，是否统一通过一个 Gameplay/Behavior 适配器，而不是能力直接持有 `BehaviorInterpreter`。
5. 能力对移动的调用是否只允许使用 UnitMover 已公开的窄接口，不允许传入 UnitMover 根对象。
6. 第一个迁移能力选择哪一个真实业务能力。

## 十一、最终评估

```text
目标方向：可行
原计划直接实施：不建议
主要阻断点：SO 共享状态、职责重复、万能 Context、生命周期缺口
推荐架构：DefinitionSO + per-owner Runtime + Component Scheduler
推荐实施：先契约、后实例、再调度、最后逐模块接入
当前代码动作：不修改
```

这套方案的核心不是“把所有单位脚本合并成一个组件”，而是：

```text
把单位能力的编排入口统一，
把运行时状态按单位和按激活实例隔离，
把具体执行继续交给现有专业模块。
```

只有这样，数据驱动才不会变成一个新的万能业务组件。
